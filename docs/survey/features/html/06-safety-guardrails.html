概要(Ignite 2025 以降の再編)

旧「コンテンツフィルター」は「Guardrails and controls」枠組みに再編された。新ドキュメントは /azure/foundry/guardrails/ 配下(※パス自体の .../guardrails/ は 404。個別記事を参照する)。ガードレール=コントロールの名前付きコレクションで、各コントロールは「リスク × 介入ポイント × アクション」で定義される。

  • 介入ポイントは4つ: User input / Tool call(プレビュー・エージェントのみ)/ Tool response(プレビュー・エージェントのみ)/ Output
  • アクションは2つ: Annotate(モデルのみ)/ Annotate and block
  • 分類器は引き続き Azure AI Content Safety のモデルを利用
  • 既定ガードレールは Microsoft.DefaultV2(編集不可。テキスト・画像生成モデルとも既定は Medium 閾値。 default-safety-policies の表)
  • モデル向けガードレールは Azure が販売する全 Foundry Models に適用(音声モデル除く)。エージェント向けガードレールはプレビューで、Foundry Agent Service のエージェントのみ対象
  • エージェントに割り当てたガードレールは、基盤モデルのガードレールを完全に上書きする
  • REST API 上の実体は従来どおり RAI policy(ARM リソース)で、デプロイの raiPolicyName で割当て。リクエスト単位の上書きは x-policy-id ヘッダー
  • (2026-09-07 追記)hosted agent は同じガードレール(RAI policy)に「Network egress controls(送信先制御・プレビュー)」を持てる(guardrails-overview 2026-07-31 版)。コンテンツ系コントロールとは別系統で、hosted agent のみ対象
  • (2026-09-26 追記)hosted agent のコンテンツセーフティはプロトコルで効き方が違う: responses プロトコルは rai_policy_name だけで効くが、invocations プロトコルは invocations_moderation(検査対象テキストがリクエスト / レスポンス本文のどこにあるかを JSONPath 風のパス / SSE セレクタで宣言)を付けないとポリシーは素通り、invocations_ws はモデレーション非対応(add-hosted-agent-guardrails 2026-09-24 版)。詳細は補足ノート 1
  • (2026-09-07 追記)サードパーティ製ガードレール(Palo Alto Networks Prisma AIRS / Zenity)を Foundry ガードレールに接続する「Third-party guardrail integrations」が GA(devblogs 2026-04-09 号「now generally available」)。詳細は下表

1. エージェント/デプロイ単位の適用と継承ルール 1つのガードレールを複数のモデルデプロイ・複数のエージェントに割当て可能。エージェントに明示割当てがない場合は基盤モデルデプロイのガードレールを継承し、明示割当てがあればモデル側設定を完全に上書き(Tool call / Tool response にコントロールがなければその経路は未スキャンになる点に注意)。Spotlighting と Groundedness はエージェント未対応で、割当てても無効化される。ガードレール処理のレイテンシは介入ポイントあたり約 50〜100ms と明記。エージェント向けのガイド付きセットアップ: guided-set-up (2026-09-07 追記) Tool call / Tool response 介入点はツール側のモデレーション対応が必要で、対応ツールは Azure AI Search / Azure Functions / OpenAPI / SharePoint Grounding / Fabric Data Agent / Bing Grounding / Bing Custom Search / Browser Automation の 8 種。一覧外のツールにはコントロールが効かないと明記(MCP・Code Interpreter・File Search は一覧に載っていない。 intervention-points 2026-03-02 版)。また hosted agent は継承ルールが異なる: 定義の rai_config を省略すると「コンテンツセーフティガードレールなしで動作」、rai_config を付けて rai_policy_name を省略すると Microsoft.DefaultV2 が適用( add-hosted-agent-guardrails 2026-06-29 版)。閉域・本番の hosted agent では割当ての明示を設計チェック項目にする。 (2026-09-26 追記) add-hosted-agent-guardrails 2026-09-24 版で次の点が追加された。(a) 存在しないポリシー ID を指定してもデプロイは成功して active になり、フィルタリングは効かない(fail-open) と警告。デプロイ時の検証を当てにせず、ポリシーの存在を確認してブロックされるか実際に試す。(b) プロトコル別の効き方: responses はポリシー指定だけで入出力を検査する。invocations はリクエスト / レスポンス本文が独自形式なので invocations_moderation(response_mode = non_streaming / streaming / both、input_paths / output_paths〈$.messages[*].content 形式〉、stream_selectors〈トップレベルの type と text_field の完全一致〉)が必須で、ないとポリシーは付いていても何も検査しない(HTTP 200 で素通りするので気づきにくい)。azure-ai-projects>=2.7.0(RaiInvocationModeration)または azd の invocationsModeration で設定する。invocations_ws はモデレーション非対応。(c) 検査の上限: リクエスト本文 2 MB 超は入力検査なしで転送、バッファ応答 1 MB 超は HTTP 502、1 回の検査は 10,000 字で切り詰め。JSON として解釈できない本文やパスが何も選ばない場合も素通り。(d) ストリーミング応答でブロックされた場合は HTTP 200 のまま event: error(code: content_filter)が 1 件送られてストリームが終わる。それまでの一部出力は利用者に届いている可能性がある。
