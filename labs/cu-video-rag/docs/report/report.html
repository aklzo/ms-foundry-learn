3. 検証の目的と範囲

ヘルプデスク AI の社内ナレッジに「画面操作手順のガイド・研修動画」が含まれる場合を想定し、 次の 3 点を定量的に確かめる。

  1. 書き起こし精度 — Content Understanding(以下 CU)の日本語音声書き起こしは、 別途 Speech to Text を実装せずに済む水準か。
  2. RAG 検索・回答精度 — CU の解析結果を AI Search に取り込んだとき、 質問に答えられる検索結果・回答が得られるか。特にナレーションでは言及されず 画面にのみ表示される情報(エラーコード・設定値・連絡先等)を扱えるか。 根拠の無い質問に捏造せず棄権できるか。
  3. コスト — 動画 1 時間あたりの CU 解析コストと、本検証全体に要した費用。

プレビュー機能は使用しない(顧客デプロイ前提)。CU は GA API 2025-11-01 のみを使用した。

6. 評価方法(指標とツール)

6.1 書き起こし: CER(文字誤り率)

CER = 編集距離 ÷ 正解文字数。正解は台本そのもの。NFKC 正規化と空白・句読点の除去後に測定 (句読点の位置は音声認識の流儀差であり意味に影響しないため)。無音動画 10 本は対象外。 prebuilt とカスタムの両方で測り、書き起こしエンジンが同一であることを確認する。

6.2 検索: 情報検索の標準指標と信頼区間

ハイブリッド検索(BM25 + ベクトル、RRF 統合)の top-5 に対して、 hit@1 / hit@3(正解動画のチャンクが 1 位 / 3 位以内)、MRR、 seg_hit@1(1 位チャンクの時間範囲が正解場面と重なる)、 ans@k(正解動画のチャンクの本文に回答値そのものが含まれる)を測る。ans@k は 「検索が当たったように見えても本文に値がなければ RAG は答えを生成できない」を測る本検証の中心指標である。 構成間の差は同一クエリ集合での対応ありブートストラップ(2,000 回)の 95% 信頼区間で示し、 区間が 0 を含まないものを有意(*)とする。

6.3 CU 出力そのものの品質: セグメント境界一致と画面転記率

検索を介さず CU 出力を直接測る 2 指標を追加した。セグメント境界一致は、CU セグメントの開始時刻と 正解ステップ境界が ±2 秒以内で対応する割合(recall = 正解境界のうち CU 境界があるもの、 precision = CU 境界のうち正解境界に対応するもの)。画面転記率は、仕込んだ画面のみ情報 67 件のうち、値が CU の生成フィールドに一字一句現れた割合(found_any)と、 表示された場面のセグメントに現れた割合(found_in_step)。

6.4 RAG 回答品質: ragas と棄権率

RAG 評価の標準ライブラリ ragas 0.4.3 を使用。検索 top-3 をコンテキストに gpt-5.4-mini で日本語回答を生成し(コンテキスト外は「分かりません」と答える指示)、 LLM-as-a-judge(gpt-4.1-mini、温度 0)で 5 指標を測定した: faithfulness(コンテキストへの忠実性)/ answer_relevancy(質問への適合)/ context_precision(上位コンテキストの適合率)/ context_recall(参照回答の根拠の網羅)/ answer_correctness(参照回答との一致)。加えて、根拠の無い U タイプ 8 問への 棄権率(「分かりません」と答えた割合。高いほど良い)と、正解のある質問への棄権率 (低いほど良い)を測る。

6.5 第 1 版(2026-09-03)からの是正点

第 1 版のレビューで見つけた評価設計の不備を是正し、全指標を再測定した。第 1 版の数値との差は 主に次の 3 点による。
  1. 回答値の衝突 — テンプレート生成の仕込み値が動画間で重複していた(「毎月 3 日」が 10 本、 「14 日間」等が 2 本ずつ。S クエリ 61 問中 16 問)。値を全動画で一意にし(部分文字列の重なりも排除)、 該当 21 本を再生成・再解析した。
  2. ans@k の定義 — 旧定義は「top-k のどれかに回答値があるか」で、別動画の同じ値でも ヒット扱いになっていた。正解動画のチャンクに限定する定義に改めた(旧定義は ans@3(any) として参考掲載)。
  3. チャンクの時間ずれ — CU はセグメントの transcriptPhrases を「フレーズの開始時刻が属する セグメント」に丸ごと付け、境界で分割しない(104 本 277 セグメント中 115 が書き起こし空)。 単語タイムスタンプでセグメントへ再配分する処理を追加した(構成 A0 = 再配分なし、A = あり)。
また、U タイプの棄権率・セグメント境界一致・画面転記率・構成間差の信頼区間・コストを新たに測定した。

読み方の注意(指標の性質)。 (1) 構成 A の faithfulness が高い(0.96)のは、 コンテキストに根拠が無いとき「分かりません」と答える設計のため (A の回答の 63/111 問が「分かりません」、C は 33/111 問)。 無回答は捏造ゼロ=忠実と評価されるので、faithfulness は context_recall / answer_correctness / 棄権率とセットで読む必要がある。 (2) answer_relevancy は「分かりません」型の回答を 0 と評価する仕様に加え、本環境では 判定 LLM が要求 3 生成に対し 1 生成しか返さず(ragas の警告)、短い事実回答(「PR-8600 Series です」等)にも 低い値が付いた。また埋め込み呼び出しの一時的な 404(DeploymentNotFound)で一部サンプルが欠損した (表の「有効 n」)。本データでは信頼性が低いため参考値とし、構成間の相対比較にのみ用いる。 (3) 総合すると、C は A に対して context_precision +0.25 / context_recall +0.40 / answer_correctness +0.18 と、 「答えるべき質問に答えられる」方向で一貫して優位。

11. 実装上の注意点(検証中に実際に踏んだ詰まりどころ)

#事象対処
1defaults へのモデル登録をモデル名で行うと、PATCH は成功するのに analyze が失敗する prebuilt アナライザーが参照するエイリアス名(prebuilt-analyzer-completion-mini 等)をキーに登録する。エラーは analyze 時まで遅延する
2カスタムアナライザーの base に prebuilt-videoSearch を指定すると 400 base に使えるのは基底 4 種のみ(prebuilt-video 等)
3親アナライザーの fieldSchema がセグメントに適用されない フィールドを持つサブアナライザーを作り、親の contentCategories から参照する 2 段構成にする(公式 analyzer-reference に記載)
4カスタムアナライザーで models.completion を省くと analyze が失敗 モデル名(デプロイ名ではない)を明示する
5既存アナライザー ID への PUT は変更が黙って無視される 実質イミュータブル。更新は DELETE → 再作成
6解析の並列実行で 429(RateLimit)が analyze の失敗として返る CU 自体でなく補完デプロイの TPM 律速。クォータ増強+指数バックオフ再試行を実装
7omitContent: true とフィールド定義は併用不可(400)omitContent: false にする
8defaults・カスタムアナライザーは Bicep に乗らないデータプレーンの状態。環境再作成時に登録を忘れると解析が全滅する セットアップスクリプトに defaults 登録(エイリアス込み)とアナライザー作成を含めて固定化
9ソフト削除 → パージ → 同名再作成したリソースでは CU の解析が「deployment or resource was not found(404)」で失敗し続けた(外部からのモデル呼び出しは正常) 別名でリソースを作り直すと即解消。検証環境の再作成は同名を避ける(公式未記載の実測)
10フレームは約 1 FPS・512×512 に縮小され、小さい文字が落ち得る(公式記載) 本検証の画面文字(25〜40px/720p)は 100% 転記できた。実動画では文字サイズに注意
11セグメントの transcriptPhrases はフレーズの開始時刻のセグメントに丸ごと付き、境界で分割されない。無音の短い話し方だと 1 フレーズが 20〜30 秒に伸び、隣のセグメントの書き起こしが空になる(277 セグメント中 115 が空)。「セグメント=チャンク」で索引すると本文と時刻がずれる 各フレーズの words[](単語タイムスタンプ)でセグメントの時間範囲へ再配分してからチャンク化する。効果: seg_hit@1 +0.117 [+0.045, +0.198]*(A0→A、95% CI)
12コストの実測には analyzerResults の usage を保存しておく videoHours / contextualizationTokens / tokens(モデル別入出力)が返る。失敗した解析は課金対象外(公式)。本レポートの §10.2 はこの合算
13セグメントが動画の先頭を覆わないと、その区間の発話が transcriptPhrases にも markdown にも出ない(password-reset: 先頭 23.6 秒・2 ステップ分が欠落、CER 46%。同じ動画が別の実行では 1.8%)。末尾でも最終文の欠落を観測。prebuilt ではセグメントの時間重複も起き、同じフレーズが 2 セグメントに付く 取り込み時にセグメントの時間軸被覆(先頭開始 ≒ 0、大きな隙間なし)を検査し、低い動画は再解析するか書き起こしを分割なしアナライザーで取り直す。フレーズ・単語は (開始, 終了, テキスト) で重複除去する。同一音声を 2 系統で書き起こして CER 差を見るのが安価な健全性検査

12. 制約と限界

  • 合成データ: 実収録より条件が良い(単一話者・雑音なし・非圧縮画面)。CER・画面文字の 転記率は上限性能。実案件では実動画でパイロット測定を行うこと(本パイプラインは流用可能)。
  • 規模: 104 本・111 クエリでの測定。S タイプ 61 問の信頼区間幅は ±0.1 程度あり、 数 % 単位の差は有意でない(§8.2)。数千本規模ではベクトル索引のチューニング (フィルタ・セマンティックランカー等)の追加検討が必要。
  • LLM-as-a-judge: ragas の値は判定 LLM(gpt-4.1-mini)に依存する相対比較として読むこと。 answer_relevancy は本データでは信頼性が低い(§9)。
  • コストは usage × 定価の概算で、契約割引・為替・単価改定で変わる。対応前の回答生成・判定トークンは 未記録のため対応後の実測で代用している。

13. 実装チームへの推奨事項

  1. 採用構成は C(日本語カスタムフィールド、2 段アナライザー)。top-3 を LLM に渡す標準的な RAG で ans@3 = 0.67。D(フィールド重み付け)は ans@k を有意に改善せず動画間の切り分けを悪化させる トレードオフがあり、top-1 しか使えない場合のみ検討。
  2. 書き起こしの別実装(Speech SDK 等)は不要。CU の出力(transcriptPhrases)をそのまま使う。
  3. チャンク単位は CU のセグメント。ただしtranscriptPhrases は words[] の時刻でセグメントへ再配分してから 本文にする(#11)。時間範囲(startTimeMs/endTimeMs)をメタデータに持たせ、回答には「動画名 + 分:秒」を引用させる。
  4. フィールド設計 3 点セット: 日本語要約(summaryJa)/ 画面内テキストの一字一句転記(screenTexts) / 操作列挙(uiActions)。description は「ミニプロンプト」として具体例を列挙する。
  5. バッチ取り込みは並列数と補完デプロイの TPM クォータをセットで設計し、429 再試行を必ず入れる。 解析ごとの usage を保存してコストを実測する(1 時間あたり約 $2.85 が目安)。
  6. 同音ドメイン語の誤認識(社給→社級 等)に備え、用語正規化辞書を後段に用意する。
  7. 回答生成には「根拠が無ければ分からないと答える」指示を入れる(U タイプ棄権率 100%)。 評価には根拠の無い質問を必ず含める。
