3. 検証の目的と範囲

ヘルプデスク AI の社内ナレッジに「画面操作手順のガイド・研修動画」が含まれる場合を想定し、 次の 2 点を定量的に確かめる。

  1. 書き起こし精度 — Content Understanding(以下 CU)の日本語音声書き起こしは、 別途 Speech to Text を実装せずに済む水準か。
  2. RAG 検索・回答精度 — CU の解析結果を AI Search に取り込んだとき、 質問に答えられる検索結果・回答が得られるか。特にナレーションでは言及されず 画面にのみ表示される情報(エラーコード・設定値・連絡先等)を扱えるか。

プレビュー機能は使用しない(顧客デプロイ前提)。CU は GA API 2025-11-01 のみを使用した。

5. データセット(104 本の設計)

日本語のナレーション付き画面操作研修動画のオープンデータセットは調査の結果存在しなかったため (PsTuts-VQA・VideoGUI はいずれも英語)、合成データセットを自作した。台本・画面・操作を プログラムで生成するため、書き起こしの正解(CER の基準)とステップ境界時刻が決定的に得られる。

形態本数内容
ナレーション付き UI 操作88 手作り 10 本(VPN・パスワード再設定・プリンタ等)+ 26 業務ドメイン × 手続きタイプのテンプレート生成 78 本
無音・テロップのみ10 ナレーションなし。字幕テロップと画面表示のみ(書き起こしが空になるケース)
スライド講義型5 講義スライド + ナレーション(UI 操作なし)
長尺・複数章構成1 約 3 分・3 章構成(セグメント分割の質の確認用)

設計上の仕掛け: (1) 約半数の動画に「画面のみ情報」(ナレーションでは「画面の注意書きを 確認してください」とだけ言い、値は画面にだけ出す)を配置。値は動画ごとに一意(内線 5xxx、ERR-1xx 等) とし、100 本規模でも回答値が衝突しない。(2) VPN と Wi-Fi と Web 会議など語彙が重なる動画を 意図的に併存させ、表層一致だけでは動画を特定できないようにした。(3) 生成はシード固定で再現可能。

評価クエリは 111 問(ナレーション由来 N: 42 / 画面のみ S: 61 / 紛らわしい C: 8)。すべてに参照回答(ref_answer)を付与し、S タイプには回答値の 文字列(answer)も付与した。

6. 評価方法(指標とツール)

6.1 書き起こし: CER(文字誤り率)

CER = 編集距離 ÷ 正解文字数。正解は台本そのもの。NFKC 正規化と空白・句読点の除去後に測定 (句読点の位置は音声認識の流儀差であり意味に影響しないため)。無音動画 10 本は対象外。

6.2 検索: 情報検索の標準指標

ハイブリッド検索(BM25 + ベクトル、RRF 統合)の top-5 に対して、 hit@1 / hit@3(正解動画のチャンクが 1 位 / 3 位以内)、MRR、 seg_hit@1(1 位チャンクの時間範囲が正解場面と重なる)、 ans@k(取得チャンク本文に回答値そのものが含まれる — 検索が「当たった」ように見えても 本文に値がなければ RAG は答えを生成できない、を測る本検証の中心指標)。

6.3 RAG 回答品質: ragas

RAG 評価の標準ライブラリ ragas 0.4.3 を使用。検索 top-3 をコンテキストに gpt-5.4-mini で日本語回答を生成し(コンテキスト外は「分かりません」と答える指示)、 LLM-as-a-judge(gpt-4.1-mini、温度 0)で 5 指標を測定した: faithfulness(コンテキストへの忠実性)/ answer_relevancy(質問への適合)/ context_precision(上位コンテキストの適合率)/ context_recall(参照回答の根拠の網羅)/ answer_correctness(参照回答との一致)。

読み方の注意(指標の性質)。 (1) 構成 A の faithfulness が高い(0.97)のは、 コンテキストに根拠が無いとき「分かりません」と答える設計のため (A の回答の 59/111 問が「分かりません」、C は 38/111 問)。 無回答は捏造ゼロ=忠実と評価されるので、faithfulness は context_recall / answer_correctness とセットで読む必要がある。 (2) answer_relevancy は「分かりません」型の回答を 0 と評価する仕様のため両構成とも低く出る。 構成間の相対比較にのみ使用する。 (3) 総合すると、C は A に対して context_precision +0.26 / context_recall +0.42 / answer_correctness +0.13 と、 「答えるべき質問に答えられる」方向で一貫して優位。

11. 実装上の注意点(検証中に実際に踏んだ詰まりどころ)

#事象対処
1defaults へのモデル登録をモデル名で行うと、PATCH は成功するのに analyze が失敗する prebuilt アナライザーが参照するエイリアス名(prebuilt-analyzer-completion-mini 等)をキーに登録する。エラーは analyze 時まで遅延する
2カスタムアナライザーの base に prebuilt-videoSearch を指定すると 400 base に使えるのは基底 4 種のみ(prebuilt-video 等)
3親アナライザーの fieldSchema がセグメントに適用されない フィールドを持つサブアナライザーを作り、親の contentCategories から参照する 2 段構成にする(公式 analyzer-reference に記載)
4カスタムアナライザーで models.completion を省くと analyze が失敗 モデル名(デプロイ名ではない)を明示する
5既存アナライザー ID への PUT は変更が黙って無視される 実質イミュータブル。更新は DELETE → 再作成
6解析の並列実行で 429(RateLimit)が analyze の失敗として返る CU 自体でなく補完デプロイの TPM 律速。クォータ増強+指数バックオフ再試行を実装
7omitContent: true とフィールド定義は併用不可(400)omitContent: false にする
8defaults・カスタムアナライザーは Bicep に乗らないデータプレーンの状態。環境再作成時に登録を忘れると解析が全滅する セットアップスクリプトに defaults 登録(エイリアス込み)とアナライザー作成を含めて固定化
9ソフト削除 → パージ → 同名再作成したリソースでは CU の解析が「deployment or resource was not found(404)」で失敗し続けた(外部からのモデル呼び出しは正常) 別名でリソースを作り直すと即解消。検証環境の再作成は同名を避ける(公式未記載の実測)
10フレームは約 1 FPS・512×512 に縮小され、小さい文字が落ち得る(公式記載) 本検証の画面文字(25〜40px/720p)は全件読めた。実動画では文字サイズに注意

12. 制約と限界

  • 合成データ: 実収録より条件が良い(単一話者・雑音なし・非圧縮画面)。CER・画面文字の 転記率は上限性能。実案件では実動画でパイロット測定を行うこと(本パイプラインは流用可能)。
  • 規模: 104 本・111 クエリでの測定。数千本規模ではベクトル索引のチューニング (フィルタ・セマンティックランカー等)の追加検討が必要。
  • LLM-as-a-judge: ragas の値は判定 LLM(gpt-4.1-mini)に依存する相対比較として読むこと。 構成間の差(A vs C)の比較には有効だが、絶対値の閾値運用には向かない。
  • 単価は変動するため、コスト見積もりは最新の料金ページ(付録)で確認すること。

13. 実装チームへの推奨事項

  1. 採用構成は C(日本語カスタムフィールド、2 段アナライザー)。top-3 を LLM に渡す標準的な RAG で ans@3 = 0.74。D(フィールド重み付け)は動画間の切り分けを悪化させる トレードオフがあり、top-1 しか使えない場合のみ検討。
  2. 書き起こしの別実装(Speech SDK 等)は不要。CU の出力(transcriptPhrases)をそのまま使う。
  3. チャンク単位は CU のセグメント。時間範囲(startTimeMs/endTimeMs)をメタデータに持たせ、 回答には「動画名 + 分:秒」を引用させる。
  4. フィールド設計 3 点セット: 日本語要約(summaryJa)/ 画面内テキストの一字一句転記(screenTexts) / 操作列挙(uiActions)。description は「ミニプロンプト」として具体例を列挙する。
  5. バッチ取り込みは並列数と補完デプロイの TPM クォータをセットで設計し、429 再試行を必ず入れる。
  6. 同音ドメイン語の誤認識(社給→社級 等)に備え、用語正規化辞書を後段に用意する。
